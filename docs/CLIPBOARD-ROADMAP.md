# 剪贴板能力对照与路线

对照对象：**Ditto**（Windows 老牌，SQLite）、**CopyQ**（跨平台，可脚本化）、
**TieZ**（同为 Tauri + Rust 的同类工具）、Windows 自带剪贴板。

这份文档的目的是**避免重复调研**：结论、取舍和"为什么不抄"都记在这里，
下次想加功能先看一眼有没有已经否决过。

## 2. 同类项目的关键设计

### Ditto（Windows，最接近我们的定位）

- **SQLite 存储**，默认 500 条，可无限；关机不丢
- 搜索支持**正则**
- **分组（Groups）**：分组树，每个分组可以绑独立快捷键
- **特殊粘贴**：纯文本、`upper/lower/sentence/capital/camel`、去多余空白、
  自动生成 slug —— 一串纯字符串处理，成本极低但天天用得上
- **多条目合并粘贴**：选中多条按顺序一次粘完
- **按应用定义粘贴键**：PuTTY 这类不认 `Ctrl+V` 的终端，单独指定 `Shift+Ins`
- 局域网同步（Friends），不走云

**最值得抄的是"特殊粘贴"和"按应用定义粘贴键"** —— 两者都是查表 + 字符串处理，
不引入任何架构负担。

### CopyQ（跨平台，能力上限最高）

- 多标签页组织（等价于 Ditto 的分组）
- 笔记 + 标签（一条数据可以带备注）
- **脚本引擎**（JS 风格）+ CLI：可以写"匹配到 URL 就打开浏览器"
- **忽略规则**：按窗口/按内容正则决定采不采
- 拖拽排序、Vim 风格编辑器、38+ 快捷键、自定义 MIME

**脚本引擎不抄**。CopyQ 是给"愿意写脚本的人"用的平台，我们的定位是
"开箱即用的截图 + 剪贴板一体工具"，加脚本引擎会带来沙箱、调试、文档三重负担。

### TieZ（同为 Tauri + Rust）

- 标签系统（多色）、Emoji 库
- 隐私遮罩预览（我们已对齐）
- **外部编辑器打开 + 保存自动回写**
- **顺序粘贴**
- 边缘停靠（贴边自动隐藏）
- SQLite + 完整的 `migrations.rs`，且对每个历史版本做升级回归测试
- WebDAV / MQTT 跨设备同步

**迁移机制值得学**。它的做法是"每个版本的库结构都能重建 → 升级 → 断言数据没丢"。
我们 `history.json` 到现在只有 `version: 1`，条目结构一变就没有退路。

### Windows 自带

只存 25 条、重启即清、无搜索。**它的存在价值是"不该比它差"** —— 这一条已经满足。

## 3. 值得做（按 ROI 排序）

### P0 · 低成本高收益

**① 特殊粘贴变换**

- 做什么：把一条记录转换后粘贴，而不是原样粘。
  首批：`纯文本`（已做）、`全部大写`、`全部小写`、`去多余空白`、`去换行合并成一段`
- 为什么：Ditto 用户最常用的就是这几个。实现是纯字符串处理，不碰存储、不碰 UI 架构
- 成本：约 100 行 Rust + 面板右键菜单
- 风险：低

**② 顺序粘贴**

- 做什么：选中多条，按顺序依次粘贴。典型场景：填表、把一串链接逐个粘到聊天框
- 为什么：TieZ / Ditto 都有，是"高频复制粘贴"场景的分水岭功能
- 成本：中等（要维护一个"待粘队列" + 每次粘贴后出队）
- 风险：中 —— 队列状态要跟面板显示同步，否则用户不知道下一条是什么

**③ 按应用适配粘贴键**

- 做什么：`deliver_to_target` 目前固定注入 `Ctrl+V`。加一张表：
  `putty.exe → Shift+Ins`、`mintty.exe → Shift+Ins`、`cmd.exe → 右键粘贴`（可选）
- 为什么：终端类程序不认 `Ctrl+V`，用户会认为"这功能在终端里坏了"
- 成本：约 40 行（一张表 + 查表）
- 风险：低

### P1 · 需要一点设计

**④ 条目就地编辑**

- 做什么：面板里 `F2` 或双击进入编辑，改完存回
- 为什么：粘之前想去掉一句话、改个数字，现在只能粘出去改
- 成本：中等（面板要加编辑态 + 失焦保存 + 转义处理）
- 风险：中 —— 编辑后 hash 变化，去重逻辑要想清楚（同内容会不会重复入库）

**⑤ 分组 / 标签 UI**

- 做什么：`tags` 字段已经有了，缺的是界面：给条目打标签、按标签筛选
- 为什么：Ditto 的分组、CopyQ 的标签页都在解决"2000 条里找常用的那 20 条"
- 成本：中等（筛选逻辑已有，主要是 UI + 拖拽）
- 风险：低
- 注意：**不要做成多标签页**。分组树在单页面板里放不下，用标签筛选更轻

**⑥ `history.json` 迁移机制**

- 做什么：`IndexFile.version` 从 1 开始真正用起来：读的时候按版本升级，
  写的时候带上新版本号；每个版本保留一个最小重建函数
- 为什么：这是**唯一一条"不做迟早出事"的**。条目字段只会越加越多，
  某天改个结构，老用户的 2000 条历史就全丢
- 成本：约 150 行 + 三组测试
- 风险：低（但必须一开始就设计对）

**⑦ 导入 / 导出**

- 做什么：导出成 JSON（含图片 base64）或纯文本清单；导入时合并去重
- 为什么：换机器、备份、迁移。Ditto 有，CopyQ 有
- 成本：低
- 风险：低

### P2 · 锦上添花

- **正则搜索**：Ditto 有。我们现在是 `contains`，2000 条量级够用。
  加正则要防 ReDoS（用户输入跑在主线程会卡界面），建议加超时或放后台
- **忽略规则**：按内容正则决定不采集。现在只有"形似密钥就跳过"和"排除程序"
- **边缘停靠**：TieZ 有。面板贴边自动隐藏，交互复杂度高，收益一般

## 4. 明确不做

| 不做 | 原因 |
|---|---|
| 脚本引擎（CopyQ 那套） | 定位是开箱即用工具，不是可编程平台。沙箱 + 调试 + 文档三份负担 |
| WebDAV / MQTT / 云同步 | 剪贴板里常年有密码、证件号、内部链接。本地常驻是这个工具的卖点 |
| 无限历史 | 现在用 JSON 索引，2000 条是合理上限。要无限就得上 SQLite，另算 |
| 主题包 / Emoji 库 | 与"截图 + 剪贴板一体工具"的定位无关 |
| 多标签页组织 | 面板尺寸小，标签树放不下。用标签筛选替代 |

---

## 5. 下一版建议的顺序

1. **⑥ 迁移机制**（唯一有"不做会丢数据"风险的）
2. **① 特殊粘贴**（半天见效）
3. **③ 粘贴键适配**（终端用户立刻有感）
4. **② 顺序粘贴**（场景最容易讲清楚）
5. 其余按用户反馈决定

前四项合起来大约 3-4 天，能把剪贴板从"够用"做到"和 Ditto 正面比不输"。
